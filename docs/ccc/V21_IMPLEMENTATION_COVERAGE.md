## Current evidence and next implementation order

- **Implemented in source:** `ClubActivity` schema; `cccActivity` save/list/transition/preflight/link operations; activity planner controls; `registrationBridge.js` policy; existing `eventRegistration` booking, SumUp and notification workflows.
- **Verified in sandbox:** 207 focused CCC tests passing and frontend build successful in the latest sandbox run; includes mocked backend handler tests for delegated access, cross-club isolation, attendance revision/audit, scoped finance and batch-query behaviour. These tests do not establish backend deployment or integration acceptance.
- **Priority 1:** Verify Base44 SDK/entity semantics in an isolated tenant. Mocked backend handler tests now cover tenant/club authority, host revocation, attendance CAS, event-scoped finance and request validation; live SDK query operators, concurrency and audit durability remain unverified.
- **Priority 2:** Link existing tenant events via an admin-selectable event list and check venue, host, capacity, eligibility, communications and payment consistency server-side. Keep public registration closed until fully verified.
- **Priority 3:** Validate `cccActivity.registration_overview` and `mark_attendance` against an isolated test tenant, including first-write attendance CAS and concurrent updates; validate delegated approval/verification actions, tenant scope, SumUp payment holds, webhooks, email delivery, waitlists and refunds without live transactions. Verify new Base44 v2 cursor pagination and batched payment reads in an isolated runtime, and performance-test the new continuation interface for datasets exceeding the initial 1,000-row request bound; host discovery now cursor-pages beyond its previous 100-activity limit.
- **Priority 4:** Verify expanded internal lifecycle (registration open/closed, in progress, completed), linked-event date/venue/capacity/payment guards and AuditLog durability; validate delegated-host workspace and venue-key mapping, complete pagination, finance, communications and remaining CCC journeys; execute A01–A20 and protected sporting regressions.

## Event booking capacity hardening (development only)
- The existing `eventRegistration` function, not merely the CCC dashboard, previously queried only 500 registration records for availability, duplicate detection and its second pre-create capacity check; alternative taster event checks were capped at 100. These reads now use tenant/club/event-scoped Base44 v2 cursor pagination with a 25,000-record safety ceiling and fail closed if the full roster cannot be verified.
- Six new tests cover 1,250 registrations, duplicate applicants beyond record 500, scoped queries, cursor stalls and incomplete reads. Actual Base44 cursor semantics and concurrency behaviour are not yet verified in an isolated runtime. The booking function remains undeployed; no live registrations have been affected.
- The existing `eventRegistration.admin_list` payment lookup has also been converted from a tenant-wide 500-record query to tenant/club/event-registration-scoped, cursor-paged payment batches, with fail-closed behaviour on incomplete data. Five additional tests cover more than 500 records, cursor paging and isolation. This is still an internal record review, not a verified SumUp settlement.
- The legacy event admin interface now pages 200 applications at a time and loads additional pages on demand, rather than returning the full event roster and payments in one response. The booking operation-ID verification and branded notice preview now bypass unnecessary full-roster reads.
- Refund selection is now linked to the registration and checkout, with ambiguous/missing transactions blocked. Refund history is cursor-paged and reconciled against the PaymentRecord refund total; a conditional PaymentRecord update marks `refund_pending` before calling SumUp, blocking competing refund attempts. On provider uncertainty the payment remains locked for manual reconciliation. Mocked backend handler tests exercise admin paging, tenant isolation, successful refund, contention and provider timeout; actual SumUp idempotency, webhook timing and recovery are **not** verified.
- Public event availability now uses two tenant/club/event-scoped Base44 count queries for active applications and unexpired payment holds, instead of scanning the full roster on every public page load. The final booking path still reads the complete roster and atomically claims capacity. The booking counter now raises an under-counted value to the observed active roster before accepting a reservation. Mocked backend tests cover more than 500 applicants, duplicate detection, capacity reconciliation and count behaviour; live concurrent bookings remain unverified.
- Follow-up review remains read-only and flags invalid/duplicate emails and missing consent/suppression/template verification; no candidate is send-eligible and no messages are queued or sent.
- All booking/finance pagination, public count queries and refund changes require actual Base44 SDK, concurrency and SumUp provider verification before deployment.

2. Verify `cccActivity` draft save/list, scoped access, revision-checked transitions and linked-event persistence against real Base44 backend; add validated host/template selectors and connect registration without duplicating the existing event service.
3. Validate actual Base44 schema, record limits and query completeness; avoid treating truncated snapshots as full totals.
4. Test initial loading, repeat navigation, stale cache, 429, slow response, lost response and simultaneous actions for membership and booking.
5. Verify permissions for super-admin, club admin, host, member, guest and cross-tenant access without weakening backend RLS.
6. Run desktop and Android browser journeys, protected sporting regressions, communication preview, and payment provider test-mode checks.
7. Obtain task-specific owner approval before any production deploy/publish or live data action; verify the live release afterwards.

## Verification language
A green unit test, lint or Vite build proves only that particular sandbox check. It does not prove Base44 function deployment, live page performance, full specification completion, or production behaviour.
